INTISARI
Pada sistem NL2SQL berbasis Large Language Model (LLM), pemberian
seluruh skema basis data (full schema) tidak selalu ideal. Skema berukuran besar dapat
memuat banyak tabel dan kolom yang tidak relevan, sehingga meningkatkan panjang
prompt dan penggunaan token. Schema pruning dapat digunakan untuk mengurangi
panjang konteks, tetapi berisiko menghilangkan kolom penting, terutama kolom kunci
dan kolom penghubung antartabel yang dibutuhkan dalam pembentukan SQL.
Penelitian ini mengevaluasi pendekatan schema pruning berbasis kolom dengan hybrid
retrieval yang menggabungkan embedding retrieval, BM25, dan Mandatory Key
Preservation (MKP). Penelitian dilakukan menggunakan dataset BIRD development set
dengan empat skenario penyajian skema, yaitu full schema, embedding retrieval, hybrid
retrieval, dan hybrid retrieval dengan MKP. Pengujian dilakukan pada LLaMA 3.2 3B
Instruct dan Gemini 2.5 Flash. Evaluasi dilakukan berdasarkan kualitas schema pruning,
execution accuracy, dan penggunaan token. Hasil penelitian menunjukkan bahwa hybrid
retrieval dengan MKP mampu menjaga struktur relasional skema lebih baik
dibandingkan hybrid retrieval tanpa MKP. Pada LLaMA 3.2 3B Instruct, metode ini
menghasilkan execution accuracy tertinggi sebesar 25,55%, sedikit lebih tinggi
dibandingkan full schema sebesar 25,10%. Pada Gemini 2.5 Flash, full schema
memperoleh akurasi tertinggi sebesar 62,39%, sedangkan hybrid retrieval dengan MKP
mampu mendekatinya dengan akurasi 61,08%. Namun, hasil uji McNemar
menunjukkan bahwa selisih antara full schema dan hybrid retrieval dengan MKP tidak
signifikan secara statistik pada kedua model. Dari sisi efisiensi, seluruh skenario schema
pruning mampu mengurangi rata-rata prompt token. Selain itu, hybrid retrieval dengan
MKP menghasilkan rata-rata total token paling rendah pada Gemini 2.5 Flash, yang
berkaitan dengan rata-rata thinking token yang lebih rendah. Temuan ini menunjukkan
bahwa optimasi konteks skema perlu menyeimbangkan efisiensi penggunaan token
dengan kelengkapan struktur relasional agar SQL dapat dihasilkan secara akurat dan
efisien.
Kata Kunci: NL2SQL, LLM, Schema Pruning, Hybrid Retrieval, Mandatory Key
Preservation (MKP)

ABSTRACT
In Large Language Model (LLM)-based NL2SQL systems, providing the entire
database schema, or full schema, is not always ideal. Large schemas may contain many
irrelevant tables and columns, increasing prompt length and token usage. Schema
pruning can be used to reduce context length, but it may also remove important
columns, particularly key columns and inter-table linking columns required for SQL
generation. This study evaluates a column-based schema pruning approach using
hybrid retrieval, which combines embedding retrieval, BM25, and Mandatory Key
Preservation (MKP). The experiments were conducted using the BIRD development set
with four schema presentation scenarios: full schema, embedding retrieval, hybrid
retrieval, and hybrid retrieval with MKP. The evaluation was performed on LLaMA 3.2
3B Instruct and Gemini 2.5 Flash based on schema pruning quality, execution accuracy,
and token usage. The results show that hybrid retrieval with MKP preserves the
relational structure of database schemas better than hybrid retrieval without MKP. On
LLaMA 3.2 3B Instruct, this method achieved the highest execution accuracy of 25.55%,
slightly higher than the full schema approach, which achieved 25.10%. On Gemini 2.5
Flash, the full schema approach achieved the highest accuracy of 62.39%, while hybrid
retrieval with MKP closely approached it with an accuracy of 61.08%. However, the
McNemar test results show that the difference between full schema and hybrid retrieval
with MKP was not statistically significant on both models. In terms of efficiency, all
schema pruning scenarios reduced the average number of prompt tokens. Furthermore,
hybrid retrieval with MKP produced the lowest average total token usage on Gemini 2.5
Flash, which was associated with lower average thinking token usage. These findings
indicate that schema context optimization should balance token efficiency with the
completeness of relational structures to support accurate and efficient SQL generation.
Keywords: NL2SQL, LLM, Schema Pruning, Hybrid Retrieval, Mandatory Key
Preservation (MKP)

BAB I
PENDAHULUAN
1.1 Latar Belakang
Perkembangan teknologi informasi yang semakin pesat telah mendorong
organisasi untuk menyimpan, mengelola, dan memanfaatkan data dalam jumlah yang
terus meningkat. Data tersebut tidak hanya berfungsi sebagai arsip operasional, tetapi
juga menjadi dasar dalam proses analisis, pelaporan, serta pengambilan keputusan.
Dalam konteks Business Intelligence (BI), data menjadi sumber utama untuk
menghasilkan informasi yang dapat membantu organisasi memahami kondisi bisnis
secara menyeluruh, mengidentifikasi pola, serta merumuskan strategi yang lebih tepat
dan responsif [1]. Kebutuhan terhadap solusi BI juga terus mengalami peningkatan,
seperti yang ditunjukkan oleh laporan Fortune Business Insight yang menyatakan bahwa
ukuran pasar global untuk BI bernilai USD 34,82 miliar pada tahun 2025 dan
diproyeksikan meningkat menjadi USD 72,21 miliar pada tahun 2034 [2]. Peningkatan
tersebut menunjukkan bahwa kemampuan mengakses dan menganalisis data secara
efektif menjadi aspek yang sangat penting dalam mendukung pengambilan keputusan
berbasis data.
Agar proses analisis dalam BI dapat dilakukan secara efektif, organisasi perlu
mengakses data yang tersimpan dalam sistem penyimpanan data. Salah satu bentuk
penyimpanan data yang banyak digunakan adalah basis data (database), khususnya
basis data relasional. Untuk memperoleh informasi dari basis data relasional, pengguna
perlu menuliskan query menggunakan Structured Query Language atau SQL. Namun,
penulisan SQL membutuhkan pemahaman terhadap struktur basis data, nama tabel,
nama kolom, relasi antartabel, dan sintaks query yang sesuai. Kondisi ini dapat menjadi
kendala bagi pengguna non-teknis karena proses eksplorasi data dan pengambilan
informasi masih sering bergantung pada pengguna teknis, seperti data analyst, data
engineer, atau database administrator [3].
Kendala tersebut menunjukkan perlunya pendekatan yang dapat menjembatani
pengguna non-teknis dengan kompleksitas penulisan SQL. Salah satu pendekatan yang
dapat digunakan adalah pemanfaatan bahasa alami sebagai antarmuka untuk mengakses
basis data. Pendekatan ini menjadi dasar bagi tugas Natural Language to SQL
(NL2SQL) atau Text-to-SQL, yaitu proses mengubah pertanyaan bahasa alami menjadi
query SQL yang dapat dieksekusi pada basis data relasional [3, 4]. Sistem NL2SQL
bertugas memahami maksud pertanyaan, mengidentifikasi tabel dan kolom yang
relevan, serta menghasilkan query SQL yang sesuai dengan struktur basis data. Dalam
konteks Natural Language to Business Intelligence (NL2BI), NL2SQL berperan sebagai

tahap awal untuk memperoleh data dari basis data sebelum data tersebut digunakan pada
proses BI lanjutan, seperti pelaporan, visualisasi, dan pembentukan insight [5]. Selain
itu, NL2SQL membantu pengguna non-teknis melakukan eksplorasi dan analisis data
secara mandiri tanpa harus memahami sintaksis SQL, sehingga dapat mengurangi
hambatan teknis dalam penggunaan sistem BI berbasis bahasa alami [4, 6].
Karena data yang digunakan dalam proses BI diperoleh melalui query SQL yang
dihasilkan oleh NL2SQL, kualitas query tersebut menjadi aspek yang perlu
diperhatikan. Jika query SQL tidak sesuai dengan maksud pertanyaan pengguna atau
tidak sesuai dengan struktur basis data, maka data yang diperoleh dapat menjadi keliru.
Kesalahan ini dapat memengaruhi proses BI berikutnya, mulai dari laporan yang tidak
akurat, visualisasi yang menyesatkan, hingga insight yang kurang tepat. Oleh sebab itu,
kualitas SQL yang dihasilkan oleh NL2SQL menjadi salah satu faktor penting agar
sistem BI dapat mendukung pengambilan keputusan secara tepat dan dapat diandalkan.
Dalam upaya menghasilkan SQL yang sesuai dengan pertanyaan pengguna,
perkembangan Large Language Model (LLM) memberikan pengaruh besar terhadap
pendekatan NL2SQL. LLM memiliki kemampuan memahami instruksi bahasa alami,
memproses konteks, serta menghasilkan teks terstruktur seperti kode dan query SQL.
Kemampuan ini membuat LLM banyak digunakan dalam tugas NL2SQL modern
karena model dapat menerima prompt yang berisi instruksi, pertanyaan, dan skema basis
data, kemudian menghasilkan SQL sebagai jawaban. Namun, keberhasilan LLM dalam
menghasilkan SQL yang benar tidak hanya bergantung pada kemampuan model, tetapi
juga sangat dipengaruhi oleh kualitas informasi yang diberikan dalam prompt. Beberapa
penelitian terkait LLM-based NL2SQL menunjukkan bahwa pendekatan modern banyak
memanfaatkan prompt engineering, pemanfaatan skema, dan strategi pemilihan konteks
untuk meningkatkan kualitas SQL yang dihasilkan [4, 7].
Salah satu informasi penting dalam prompt NL2SQL adalah skema basis data.
Skema basis data menjadi konteks utama bagi model untuk menentukan tabel, kolom,
dan relasi yang relevan dalam pembentukan query SQL. Tanpa skema yang tepat, model
dapat menghasilkan nama tabel atau kolom yang tidak valid, memilih relasi yang salah,
atau membentuk query yang tidak sesuai dengan basis data. Penyajian skema kepada
LLM menjadi faktor penting dalam keberhasilan NL2SQL.
Namun, kebutuhan terhadap informasi skema tidak berarti bahwa seluruh skema
basis data (full schema) selalu perlu diberikan kepada LLM. Pada basis data berukuran
besar, full schema dapat berisi banyak tabel dan kolom yang tidak semuanya relevan
terhadap pertanyaan. Kondisi ini menyebabkan prompt menjadi lebih panjang dan
meningkatkan jumlah token yang harus diproses oleh model. Dalam konteks LLM,
token merupakan satuan teks yang diproses oleh model, baik pada masukan maupun
keluaran [8]. Semakin panjang skema yang dimasukkan ke dalam prompt, semakin
2

--- PAGE 16 ---
besar pula jumlah token yang digunakan. Hal ini dapat meningkatkan biaya inferensi
pada model berbasis API, memperbesar kebutuhan komputasi pada model lokal, serta
membuat model harus memproses banyak informasi yang kurang relevan [9].
Untuk mengatasi permasalahan tersebut, salah satu pendekatan yang dapat
digunakan adalah schema pruning. Schema pruning bertujuan mengurangi informasi
skema yang diberikan kepada model dengan mempertahankan tabel dan kolom yang
relevan terhadap pertanyaan. Dengan cara ini, prompt menjadi lebih ringkas dan model
dapat lebih fokus pada bagian basis data yang dibutuhkan. Namun, proses ini perlu
dilakukan secara hati-hati karena informasi relasional seperti primary key, foreign key,
dan hubungan antartabel tetap dibutuhkan dalam pembentukan query SQL, terutama
ketika query membutuhkan operasi join antartabel [10]. Jika informasi penting tersebut
ikut terhapus, model dapat kehilangan konteks yang dibutuhkan untuk menghasilkan
SQL yang benar.
Dalam pengembangan NL2SQL modern, tantangan pemilihan bagian skema
yang relevan banyak dibahas melalui pendekatan schema linking dan schema pruning.
Penelitian terdahulu menunjukkan bahwa proses pemilihan skema pada NL2SQL
semakin banyak memanfaatkan kemampuan LLM untuk melakukan identifikasi elemen
skema yang relevan terhadap pertanyaan pengguna [11,12]. Pendekatan tersebut mampu
memanfaatkan kemampuan pemahaman bahasa alami yang dimiliki LLM, tetapi juga
menambah kebutuhan komputasi dan biaya inferensi karena LLM digunakan tidak
hanya untuk menghasilkan SQL, melainkan juga pada tahap pemilihan konteks skema.
Di sisi lain, pendekatan retrieval-based yang lebih ringan berpotensi mengurangi
kebutuhan komputasi, tetapi masih menghadapi tantangan dalam mempertahankan
informasi relasional penting yang diperlukan untuk pembentukan SQL. Selain itu,
pemilihan skema dapat dilakukan pada tingkat tabel maupun tingkat kolom. Pemilihan
pada tingkat tabel dapat mengurangi cakupan skema, tetapi masih menyertakan seluruh
kolom dari tabel yang terpilih. Sebaliknya, pemilihan pada tingkat kolom
memungkinkan konteks skema disusun secara lebih spesifik karena hanya kolom yang
diprediksi relevan yang disertakan, tetapi memiliki risiko menghilangkan kolom penting
yang tidak disebutkan secara eksplisit dalam pertanyaan, seperti primary key, foreign
key, atau kolom penghubung relasi antartabel.
Berdasarkan kondisi tersebut, masih diperlukan kajian mengenai penggunaan
schema pruning berbasis kolom yang memanfaatkan mekanisme retrieval non-LLM
untuk memilih kolom yang relevan, sekaligus mempertahankan informasi relasional
melalui mekanisme Mandatory Key Preservation (MKP). Kajian ini diperlukan untuk
memahami pengaruh pendekatan tersebut terhadap kualitas SQL yang dihasilkan serta
efisiensi penggunaan token pada model LLM dengan karakteristik yang berbeda.
Penelitian ini berfokus pada optimasi penyajian skema melalui schema pruning

1.2 Rumusan Masalah
Berdasarkan latar belakang yang telah dijelaskan, penelitian ini berangkat dari
kebutuhan untuk menyajikan konteks skema yang lebih ringkas tanpa menghilangkan
informasi penting yang dibutuhkan dalam pembentukan query SQL. Oleh karena itu,
rumusan masalah dalam penelitian ini adalah sebagai berikut.
1. Beberapa pendekatan schema linking atau schema pruning menggunakan LLM
dalam proses pemilihan elemen skema, sehingga berpotensi menambah
penggunaan token sebelum proses pembangkitan SQL dilakukan.
2. Schema pruning dapat mengurangi ukuran konteks skema, tetapi pemilihan kolom
berdasarkan relevansi pertanyaan saja berisiko menghilangkan kolom kunci atau
kolom penghubung yang dibutuhkan untuk menjaga relasi antartabel.
3. Pengaruh schema pruning terhadap efisiensi penggunaan token dan kualitas SQL
masih perlu dievaluasi pada model LLM dengan karakteristik berbeda, karena
setiap model dapat memiliki kemampuan yang berbeda dalam memanfaatkan
konteks skema yang telah dipangkas.
1.3 Tujuan Penelitian
Berdasarkan rumusan masalah yang telah dirumuskan, penelitian ini bertujuan
untuk mengevaluasi penerapan schema pruning pada tugas NL2SQL berbasis LLM.
Secara khusus, tujuan penelitian ini dijabarkan sebagai berikut.
1. Menerapkan pendekatan schema pruning berbasis kolom dengan embedding
retrieval dan hybrid retrieval embedding-BM25 sebagai dasar pemilihan kolom,
tanpa menggunakan LLM sebagai komponen utama dalam proses seleksi skema.
2. Menerapkan Mandatory Key Preservation (MKP) untuk mempertahankan kolom
kunci yang berada pada jalur relasi antartabel yang relevan agar informasi
relasional tetap terjaga setelah proses schema pruning.
3. Mengevaluasi pengaruh schema pruning terhadap kualitas SQL dan efisiensi
penggunaan token dibandingkan dengan penggunaan full schema pada model
LLM dengan karakteristik yang berbeda.

TINJAUAN PUSTAKA DAN DASAR TEORI
2.1 Tinjauan Pustaka
Seiring berkembangnya LLM, penelitian NL2SQL dilakukan melalui berbagai
pendekatan, mulai dari fine-tuning, prompting dan in-context learning, hingga schema
linking dan schema pruning. Setiap pendekatan memiliki fokus yang berbeda, baik dalam
meningkatkan kemampuan model, menyusun konteks masukan, maupun memilih bagian
skema yang relevan agar model dapat menghasilkan SQL dengan lebih tepat.
2.1.1 NL2SQL dengan Pendekatan Berbasis Fine-tuning
Pendekatan berbasis fine-tuning dilakukan dengan melatih kembali model bahasa
menggunakan data yang sesuai dengan tugas NL2SQL. Data pelatihan umumnya terdiri
atas pasangan pertanyaan bahasa alami, skema basis data, dan query SQL. Melalui
proses ini, model diharapkan dapat mempelajari hubungan antara pertanyaan pengguna,
struktur basis data, serta bentuk SQL yang perlu dihasilkan. Pendekatan ini bertujuan
untuk mengatasi keterbatasan model bahasa umum dalam memahami struktur basis
data, seperti pemilihan tabel dan kolom, penggunaan kondisi filter, agregasi, serta
penyusunan relasi join.
Salah satu penelitian yang menggunakan pendekatan ini adalah CodeS oleh Li et
al. [15]. CodeS dikembangkan sebagai model bahasa sumber terbuka yang diarahkan
secara khusus untuk tugas NL2SQL. Penelitian ini berawal dari banyaknya sistem
NL2SQL dengan performa tinggi yang masih bergantung pada model tertutup seperti
GPT atau Claude. Ketergantungan tersebut memiliki keterbatasan dari sisi transparansi,
privasi data, dan biaya inferensi. Untuk mengatasi hal tersebut, CodeS dibangun melalui
beberapa tahap, yaitu incremental pre-training menggunakan korpus yang berfokus
pada SQL, penyusunan prompt berbasis skema, serta supervised fine-tuning agar model
lebih mampu menghasilkan SQL sesuai pertanyaan dan struktur basis data.
Hasil evaluasi CodeS menunjukkan bahwa fine-tuning dapat meningkatkan
performa model sumber terbuka pada tugas NL2SQL. Pada Spider development set,
performa CodeS meningkat dari SFT CodeS-1B hingga SFT CodeS-7B, dengan SFT
CodeS-7B memperoleh execution accuracy sebesar 85,4% dan test-suite accuracy
sebesar 80,3% [15]. Capaian ini menunjukkan bahwa model sumber terbuka yang
dilatih secara khusus dapat bersaing dengan beberapa pendekatan berbasis model
tertutup pada benchmark tertentu. Namun, hasil CodeS juga menunjukkan bahwa
peningkatan ukuran model tidak selalu menghasilkan performa yang lebih baik. SFT
CodeS-15B memperoleh hasil yang sedikit lebih rendah dibandingkan SFT CodeS-7B,
9

--- PAGE 23 ---
sehingga jumlah parameter bukan satu-satunya faktor yang menentukan kinerja
model [15]. Faktor seperti kualitas data pelatihan, kesesuaian data dengan tugas, dan
strategi pelatihan tetap berpengaruh terhadap hasil akhir.
Selain itu, CodeS juga menunjukkan bahwa pendekatan fine-tuning masih
memiliki tantangan dalam hal generalisasi lintas domain. Model yang dilatih
menggunakan Spider mengalami penurunan performa ketika dievaluasi pada domain
real-world seperti Bank-Financials dan Aminer-Simplified. Performa tersebut
meningkat setelah model menggunakan data augmentasi domain [15]. Temuan ini
menunjukkan bahwa model hasil fine-tuning dapat bekerja dengan baik pada domain
yang serupa dengan data pelatihan, tetapi performanya dapat menurun ketika diterapkan
pada skema atau domain yang berbeda.
Penelitian lain yang termasuk dalam pendekatan ini adalah SQL-R1 oleh Ma et
al. [16]. Berbeda dari supervised fine-tuning, SQL-R1 menggunakan reinforcement
learning untuk meningkatkan kemampuan penalaran model dalam tugas NL2SQL.
Penelitian ini berangkat dari permasalahan bahwa supervised fine-tuning cenderung
membuat model meniru pola SQL dari data pelatihan, tetapi belum tentu meningkatkan
kemampuan penalaran model pada pertanyaan yang lebih kompleks. Oleh karena itu,
SQL-R1 menggunakan fungsi reward yang mempertimbangkan beberapa aspek, seperti
format SQL, hasil eksekusi, hasil keluaran, dan panjang SQL.
Hasil evaluasi SQL-R1 menunjukkan bahwa pelatihan berbasis reinforcement
learning dapat meningkatkan performa model pada tugas NL2SQL. Pada
Qwen2.5-Coder-7B, SQL-R1 meningkatkan execution accuracy pada beberapa
benchmark, termasuk Spider dan BIRD. Salah satu hasil utamanya terlihat pada Spider
dev, dengan peningkatan akurasi dari 77,4% menjadi 87,6% [16]. Selain itu, studi ablasi
menunjukkan bahwa komponen reward seperti format score, execution score, result
score, dan length score berkontribusi terhadap performa model. Pada eksperimen ablasi
tersebut, setiap komponen dihapus secara bergantian dari fungsi reward yang digunakan
pada tahap pelatihan. Hasilnya, akurasi pada BIRD dev mengalami penurunan
dibandingkan ketika seluruh komponen reward digunakan [16]. Temuan ini
menunjukkan bahwa umpan balik berbasis reward dapat membantu model
menghasilkan SQL yang lebih sesuai, baik dari sisi format, hasil eksekusi, maupun
kompleksitas query.
Berdasarkan penelitian-penelitian tersebut, pendekatan berbasis fine-tuning
menunjukkan bahwa pelatihan khusus pada data NL2SQL dapat meningkatkan
kemampuan model dalam memahami hubungan antara pertanyaan bahasa alami, skema
basis data, dan struktur SQL. CodeS memperlihatkan bahwa supervised fine-tuning
dapat membuat model sumber terbuka lebih kompetitif pada benchmark NL2SQL,
sedangkan SQL-R1 menunjukkan bahwa peningkatan performa juga dapat diperoleh

performa yang sama ketika diterapkan pada skema atau domain yang berbeda.
2.1.2 NL2SQL dengan Pendekatan Berbasis Prompting dan In-context Learning
Berbeda dari pendekatan fine-tuning, pendekatan berbasis prompting dan
in-context learning memanfaatkan kemampuan LLM tanpa melakukan pelatihan ulang
model. Pada pendekatan ini, model diberikan instruksi, skema basis data, serta contoh
pasangan pertanyaan-SQL di dalam prompt. Kualitas SQL yang dihasilkan sangat
dipengaruhi oleh cara representasi skema, kejelasan instruksi, pemilihan contoh, dan
urutan penyajian informasi di dalam prompt.
Salah satu penelitian awal yang mengevaluasi kemampuan LLM untuk tugas
NL2SQL adalah Rajkumar et al. [17]. Penelitian tersebut mengevaluasi Codex pada
beberapa benchmark NL2SQL, terutama Spider, dengan variasi informasi yang
dimasukkan ke dalam prompt. Hasil penelitian menunjukkan bahwa representasi skema
memiliki pengaruh besar terhadap performa model. Pada Spider dev, prompt yang hanya
berisi pertanyaan menghasilkan execution accuracy sebesar 8,3%. Akurasi meningkat
menjadi 59,9% ketika skema direpresentasikan dalam bentuk CREATE TABLE, dan
mencapai 67,0% ketika representasi tersebut dilengkapi dengan contoh konten basis
data [17]. Temuan ini menunjukkan bahwa LLM membutuhkan informasi skema yang
cukup eksplisit agar dapat menghasilkan SQL yang sesuai dengan struktur basis data.
Hasil terbaik Codex pada penelitian tersebut menunjukkan performa yang
kompetitif meskipun model tidak melalui proses fine-tuning. Pada Spider dev, capaian
Codex mendekati beberapa model yang telah dilatih secara khusus, seperti BRIDGE v2
dan T5-large, meskipun masih berada di bawah pendekatan fine-tuning yang lebih kuat
seperti T5-3B + PICARD [17]. Dengan demikian, penelitian ini menunjukkan bahwa
pendekatan berbasis prompting dapat menjadi baseline yang kuat, tetapi belum
sepenuhnya menggantikan pendekatan fine-tuning pada benchmark yang lebih
kompleks.
Pada skenario few-shot, penambahan contoh pertanyaan-SQL juga membantu
model beradaptasi pada domain tertentu. Contoh yang diberikan di dalam prompt dapat
membantu model memahami pola pemetaan dari pertanyaan bahasa alami ke SQL.

Penelitian lain yang lebih sistematis dilakukan oleh Gao et al. melalui

2.1.3 NL2SQL dengan Pendekatan Berbasis Schema Linking dan Schema
Pruning
Pendekatan berbasis prompting menunjukkan bahwa informasi skema yang
diberikan kepada model memiliki pengaruh penting terhadap kualitas SQL yang
dihasilkan. Namun, penyajian skema dalam prompt juga dapat menjadi tantangan ketika
basis data memiliki ukuran yang besar. Jika seluruh skema dimasukkan ke dalam
prompt, jumlah token dapat menjadi besar dan model dapat menerima terlalu banyak
informasi yang tidak relevan. Sebaliknya, jika skema terlalu banyak dipangkas, tabel
atau kolom penting dapat hilang sehingga SQL yang dihasilkan menjadi salah. Untuk
mengatasi tantangan tersebut, pendekatan schema linking dan schema pruning berfokus
pada pemilihan bagian skema basis data yang paling relevan dengan pertanyaan
pengguna. Pendekatan ini perlu menjaga keseimbangan antara mengurangi konteks
yang tidak relevan dan mempertahankan informasi penting dari skema basis data.
Salah satu penelitian yang relevan adalah SchemaGraphSQL oleh Safdarian et
al. [11]. Penelitian ini berangkat dari permasalahan bahwa pemilihan tabel dan kolom
tidak cukup hanya berdasarkan kemiripan makna dengan pertanyaan pengguna. Pada
pertanyaan yang membutuhkan beberapa tabel, sistem juga perlu mempertahankan
hubungan antartabel agar proses join dapat dibuat dengan benar. SchemaGraphSQL
merepresentasikan skema basis data dalam bentuk graf, dengan tabel sebagai simpul
(node) dan relasi foreign key sebagai sisi (edge). Selanjutnya, LLM digunakan untuk
menentukan tabel sumber dan tabel tujuan dari pertanyaan pengguna. Setelah itu,
algoritma pencarian jalur digunakan untuk menemukan hubungan antartabel yang
relevan, dan hasilnya digunakan untuk menentukan tabel beserta dengan elemen
kolomnya yang dimasukkan ke dalam konteks SQL generation [11].
Hasil penelitian menunjukkan bahwa SchemaGraphSQL dapat meningkatkan
kinerja pada BIRD development split. Konfigurasi utama yang digunakan adalah
force-union, yaitu strategi yang mengambil gabungan semua jalur terpendek antara tabel
sumber dan tabel tujuan yang diprediksi oleh LLM, tanpa memilih satu jalur tertentu.
Pada metrik schema linking, konfigurasi ini memperoleh recall sebesar 95,71% dan F6
sebesar 95,43% [11]. Pada evaluasi execution accuracy, penggunaan Gemini 2.5 Flash
sebagai SQL generator meningkat dari 51,50% pada baseline menjadi 62,91% dengan
SchemaGraphSQL force-union [11]. Temuan ini menunjukkan bahwa pemanfaatan

--- PAGE 27 ---
struktur graf dapat membantu proses pemilihan skema, terutama pada pertanyaan yang
membutuhkan relasi antartabel. Meskipun demikian, SchemaGraphSQL masih
menggunakan LLM pada tahap awal untuk menentukan tabel sumber dan tabel tujuan.
Hal ini dapat menambah jumlah pemanggilan LLM serta meningkatkan penggunaan
token dan biaya inferensi.
Penelitian lain yang relevan adalah The Death of Schema Linking? Text-to-SQL
in the Age of Well-Reasoned Language Models oleh Maamari et al. [12]. Penelitian ini
membahas kembali anggapan bahwa schema linking selalu meningkatkan kinerja
NL2SQL. Permasalahan utama yang dikaji adalah adanya pilihan sulit antara
mengurangi bagian skema yang tidak relevan dan risiko menghilangkan bagian skema
yang sebenarnya penting. Metode penelitian yang digunakan adalah menguji beberapa
strategi schema linking pada benchmark BIRD, lalu membandingkan pengaruhnya
terhadap berbagai LLM dengan kemampuan yang berbeda. Strategi yang diuji
mencakup pemilihan kolom secara langsung, pemilihan tabel terlebih dahulu kemudian
kolom, serta beberapa variasi hybrid untuk menjaga recall skema [12].
Hasil penelitian tersebut menunjukkan bahwa manfaat schema linking
bergantung pada kemampuan model yang digunakan. Pada model yang lebih kuat,
seperti fine-tuned GPT-4o, pipeline tanpa schema linking memperoleh execution
accuracy sebesar 67,35%. Ketika ditambahkan Table-to-Column Schema Linking
(TCSL), akurasi turun menjadi 62,58% [12]. Penurunan ini menunjukkan bahwa proses
penyaringan skema dapat menghapus kolom penting, padahal model besar sebenarnya
sudah cukup mampu memilih kolom yang relevan dari skema lengkap. Dengan kata
lain, pengurangan konteks yang terlalu agresif dapat mengurangi informasi penting yang
dibutuhkan untuk menghasilkan SQL yang benar.
Sebaliknya, pada model yang lebih kecil atau model dengan kemampuan SQL
generation yang lebih rendah, schema linking dapat membantu meningkatkan performa.
Model yang lebih kecil cenderung lebih mudah terganggu oleh skema yang panjang dan
informasi yang tidak relevan. Dengan mengurangi bagian skema yang tidak dibutuhkan,
schema linking dapat membantu model lebih fokus pada tabel dan kolom yang berkaitan
dengan pertanyaan. Namun, manfaat ini tetap bergantung pada kualitas proses pemilihan
skema. Jika proses penyaringan terlalu agresif, kolom penting dapat ikut terhapus dan
hasil SQL tetap dapat menjadi salah [12].
Maamari et al. juga menunjukkan adanya hubungan antara pengurangan
informasi tidak relevan dan penurunan recall. Pada skema penuh, recall tetap 100%
karena seluruh kolom penting tersedia, tetapi false positive rate mencapai 94,62%.
Sebaliknya, TCSL mampu menurunkan false positive rate menjadi 9,79%, tetapi recall
turun menjadi 77,44% [12]. Temuan ini menunjukkan bahwa schema linking tidak
selalu memberikan hasil yang lebih baik, karena keberhasilannya dipengaruhi oleh

kemampuan model, ukuran skema, dan kualitas metode penyaringan skema.
Berdasarkan kedua penelitian tersebut, pendekatan schema linking dan schema
pruning menunjukkan bahwa pemilihan skema merupakan aspek penting dalam tugas
NL2SQL, terutama ketika skema basis data berukuran besar atau memiliki banyak relasi
antartabel. Kelebihan pendekatan ini terletak pada kemampuannya untuk mengurangi
informasi skema yang tidak relevan sehingga konteks masukan menjadi lebih ringkas
dan model dapat lebih fokus pada tabel serta kolom yang berkaitan dengan pertanyaan
pengguna. SchemaGraphSQL memperlihatkan bahwa representasi skema dalam bentuk
graf dapat membantu mempertahankan relasi antartabel, sehingga berguna pada
pertanyaan yang membutuhkan operasi join. Namun, pendekatan ini juga memiliki
keterbatasan karena kinerjanya sangat bergantung pada kualitas proses pemilihan skema.
Jika proses seleksi terlalu agresif, tabel atau kolom penting dapat terhapus sehingga
SQL yang dihasilkan menjadi salah. Selain itu, hasil Maamari et al. menunjukkan
bahwa schema linking tidak selalu meningkatkan performa pada semua jenis model.
Pada model yang lebih kuat, penggunaan skema lengkap dapat lebih menguntungkan
karena model masih mampu memilih elemen skema yang relevan secara mandiri.
Sebaliknya, pada model yang lebih kecil, penyaringan skema dapat membantu
mengurangi gangguan dari informasi tidak relevan, tetapi tetap membutuhkan
mekanisme yang mampu mempertahankan kolom penting dan relasi antartabel.
2.2 Dasar Teori
2.2.1 Database / Basis Data
Basis data (database) adalah kumpulan data yang saling berkaitan dan disimpan
secara terstruktur sehingga dapat dikelola untuk mendukung kebutuhan informasi suatu
organisasi atau aplikasi. Pengelolaan basis data umumnya dilakukan melalui Database
Management System (DBMS), yaitu perangkat lunak yang menyediakan mekanisme
untuk membuat, menyimpan, mengatur, mengakses, dan mengelola data di dalam basis
data [19, 20].
Salah satu model basis data yang banyak digunakan adalah model relasional.
Pada model ini, data direpresentasikan dalam bentuk relasi atau tabel yang terdiri atas
baris dan kolom. Setiap baris merepresentasikan satu rekaman data atau tuple,
sedangkan setiap kolom merepresentasikan atribut dari data tersebut. Model relasional
memungkinkan data dari beberapa tabel dihubungkan melalui primary key dan foreign
key. Struktur tersebut membuat basis data relasional mampu merepresentasikan
hubungan antardata secara terorganisasi dan mendukung proses pengambilan informasi
melalui operasi query [19, 21, 22].
Hubungan antara basis data, skema basis data, dan SQL dapat dipahami sebagai
tiga komponen yang saling berkaitan. Basis data berfungsi sebagai tempat penyimpanan

digunakan untuk mengakses dan mengelola data berdasarkan struktur tersebut. Dengan
demikian, SQL perlu disusun dengan mengacu pada skema basis data agar query yang
dibuat sesuai dengan tabel, kolom, dan relasi yang tersedia. Hubungan ketiga komponen

Management System (RDBMS), termasuk untuk menambahkan, memperbarui,
menghapus, dan mengambil data pada basis data relasional [23]. Selain itu, SQL juga

INSERT, UPDATE, dan DELETE. Selain itu, SQL juga mendukung operasi agregasi,
pengurutan, pengelompokan, subquery, serta join antartabel. Kemampuan tersebut

2.2.1.2 Skema Basis Data
Skema basis data adalah struktur yang mendeskripsikan bagaimana data
disimpan dan dihubungkan dalam sebuah basis data. Skema umumnya mencakup nama
tabel, nama kolom, tipe data, primary key (PK), foreign key (FK), serta relasi antartabel.
Pada basis data relasional, skema dapat dipahami sebagai representasi struktur basis data
17

--- PAGE 31 ---
yang menunjukkan tabel yang tersedia, kolom yang dimiliki setiap tabel, tipe data yang
digunakan, dan relasi antartabel. Dengan adanya skema, pengguna atau sistem dapat
menentukan bagian basis data yang perlu digunakan agar query SQL yang dibuat sesuai
dengan struktur data yang tersedia [19, 22, 25].
Dalam tugas NL2SQL, skema basis data menjadi bagian penting dari masukan
model karena model perlu memahami elemen basis data yang dapat digunakan untuk
menjawab pertanyaan pengguna. Misalnya, ketika pengguna menanyakan jumlah
transaksi dari suatu pelanggan, model perlu mengetahui tabel yang menyimpan data
pelanggan, tabel yang menyimpan transaksi, kolom yang merepresentasikan jumlah,
serta relasi yang menghubungkan kedua tabel tersebut. Skema tidak hanya berfungsi
sebagai gambaran susunan basis data, tetapi juga sebagai konteks yang membantu
model menentukan komponen SQL yang relevan [14, 24].
2.2.2 Text-to-SQL / Natural Language to SQL (NL2SQL)
Text-to-SQL atau Natural Language to SQL (NL2SQL) adalah tugas
menerjemahkan pertanyaan bahasa alami menjadi query SQL yang dapat dieksekusi
pada basis data relasional [3, 4]. Pendekatan ini bertujuan memudahkan pengguna
memperoleh informasi dari basis data tanpa harus menulis SQL secara manual. Dengan
pendekatan tersebut, pengguna dapat mengajukan pertanyaan seperti “berapa jumlah
pelanggan pada setiap kota”, kemudian sistem menghasilkan query SQL yang sesuai
dengan skema basis data [24, 26].
Penelitian NL2SQL berkembang dari pendekatan awal berbasis natural
language interface to database, pendekatan semantic parsing, model
sequence-to-sequence, hingga pendekatan yang memanfaatkan Large Language Model
(LLM) [4, 26, 27]. Perkembangan tersebut menunjukkan bahwa NL2SQL tidak hanya
merupakan persoalan penerjemahan bahasa alami ke SQL, tetapi juga tugas yang
memerlukan pemahaman terhadap struktur basis data. Dalam perkembangannya,
beberapa dataset seperti WikiSQL dan Spider banyak digunakan sebagai benchmark
untuk melatih dan mengevaluasi model NL2SQL [24, 26]. Selanjutnya, BIRD
diperkenalkan sebagai benchmark yang lebih baru dengan karakteristik basis data yang
lebih kompleks dan lebih mendekati skenario nyata [14].
Seiring berkembangnya LLM, pendekatan NL2SQL mulai banyak
memanfaatkan kemampuan model besar dalam memahami instruksi bahasa alami dan
menghasilkan keluaran terstruktur seperti SQL [4, 18]. LLM dapat digunakan dalam
tugas NL2SQL melalui beberapa strategi, seperti prompting, in-context learning,
fine-tuning, maupun kombinasi dengan teknik pemilihan konteks skema. Meskipun
LLM menunjukkan kemampuan yang menjanjikan, tugas NL2SQL tetap menantang
karena SQL yang dihasilkan harus sesuai dengan pertanyaan pengguna, mengikuti

struktur skema basis data, dan menghasilkan keluaran yang benar ketika
dieksekusi [14, 18]. Hal ini menunjukkan bahwa keberhasilan NL2SQL tidak hanya

menggunakan informasi skema dan membentuk logika SQL.
Tantangan utama dalam NL2SQL meliputi pemahaman pertanyaan pengguna,
pemetaan istilah dalam pertanyaan ke tabel dan kolom, pemilihan kondisi filter,

kompleks karena model harus mempertimbangkan skema, isi basis data, dan informasi
tambahan yang relevan untuk menghasilkan SQL yang benar [14].
2.2.3 Large Language Model (LLM)
Large Language Model (LLM) adalah model bahasa berbasis neural network
yang dilatih menggunakan data teks dalam jumlah besar untuk memahami dan
menghasilkan bahasa alami [28]. Melalui proses pelatihan tersebut, LLM belajar
mengenali pola dalam teks, memahami konteks kalimat, dan menghasilkan jawaban
yang sesuai dengan masukan pengguna. Dengan kemampuan tersebut, LLM dapat
dimanfaatkan untuk berbagai tugas pemrosesan bahasa alami, seperti menjawab
pertanyaan, merangkum teks, menerjemahkan bahasa, mengklasifikasikan teks, serta
menghasilkan teks atau kode program.
Sebagian besar LLM modern dibangun dengan arsitektur transformer. Arsitektur
ini menggunakan mekanisme attention untuk memproses urutan teks [29]. Sebelum
diproses oleh model, teks diubah terlebih dahulu menjadi satuan-satuan kecil yang
disebut token melalui proses tokenisasi. Model kemudian mengolah urutan token
tersebut dan menghasilkan keluaran dengan memprediksi token berikutnya berdasarkan
token-token sebelumnya [30].
Salah satu karakteristik penting LLM adalah kemampuannya menggunakan
prompt sebagai masukan. Prompt dapat memuat instruksi, pertanyaan, informasi
tambahan, atau contoh keluaran yang diharapkan. Melalui prompt, LLM dapat
diarahkan untuk menyelesaikan berbagai tugas tanpa harus selalu dilatih ulang secara
khusus untuk setiap tugas. Dalam konteks NL2SQL, kemampuan ini memungkinkan
LLM menghasilkan query SQL berdasarkan pertanyaan pengguna dan informasi skema
yang diberikan.

2.2.3.1 Token
Token merupakan unit kecil dari teks yang digunakan LLM dalam memproses
bahasa. Sebelum diproses oleh model, teks melalui proses tokenisasi, yaitu pemecahan
rangkaian simbol atau teks menjadi unit-unit yang lebih kecil yang disebut token [31].
Token dapat berupa kata, potongan kata, huruf, angka, tanda baca, maupun simbol
tertentu [32]. Dokumentasi Gemini juga menjelaskan bahwa token dapat berupa
karakter tunggal atau kata utuh, sedangkan kata yang panjang dapat dipecah menjadi
beberapa token [8]. Token-token tersebut kemudian diubah menjadi representasi
numerik agar dapat diproses oleh neural network.
Jumlah token menentukan banyaknya informasi yang dapat diberikan kepada
LLM. Setiap model memiliki batas maksimum token yang dapat diproses, yang
umumnya disebut batas konteks, context length, atau context window [8, 33]. Jika
masukan terlalu panjang, sebagian informasi dapat terpotong atau tidak dapat
dimasukkan ke dalam konteks model. Oleh karena itu, semakin panjang instruksi,
pertanyaan, atau informasi tambahan yang diberikan, semakin banyak token yang
digunakan. Dalam tugas NL2SQL, token dapat berasal dari instruksi, pertanyaan
pengguna, contoh keluaran, dan skema basis data yang dimasukkan ke dalam prompt.
Selain memengaruhi panjang konteks yang diproses model, jumlah token juga berkaitan
dengan efisiensi penggunaan model berbasis API karena biaya pemanggilan API dapat
dipengaruhi oleh jumlah token masukan dan keluaran [8].
2.2.3.2 LLaMA 3.2 3B
LLaMA atau Large Language Model Meta AI adalah keluarga model bahasa
yang dikembangkan oleh Meta. LLaMA 3.2 merupakan kumpulan model bahasa
generatif multibahasa yang tersedia dalam beberapa ukuran. Pada rilis LLaMA 3.2,
Meta menyediakan model berbasis teks ringan berukuran 1B dan 3B parameter, serta

Varian LLaMA 3.2 3B termasuk model berbasis teks, sehingga masukan dan keluaran
utamanya berupa teks.
Model LLaMA 3.2 3B tersedia dalam bentuk pre-trained dan instruction-tuned.
Varian instruction-tuned dirancang agar lebih mampu mengikuti instruksi pengguna
dalam bahasa alami. Berdasarkan dokumentasi model, LLaMA 3.2 3B dioptimalkan
untuk beberapa penggunaan berbasis teks, seperti dialog multibahasa, peringkasan, dan

dapat menghasilkan teks bebas, tetapi juga dapat diarahkan untuk memberikan respons
berdasarkan instruksi dan konteks tertentu.
LLaMA 3.2 3B dapat dipandang sebagai LLM berukuran kecil atau ringan yang

2.2.3.3 Gemini 2.5 Flash
Gemini adalah keluarga model generatif yang dikembangkan oleh Google untuk

Sebagai model generatif, Gemini 2.5 Flash dapat digunakan untuk berbagai
tugas berbasis bahasa, seperti menjawab pertanyaan, mengikuti instruksi, menganalisis
teks, merangkum informasi, dan menghasilkan kode. Keunggulan utama model ini
terletak pada keseimbangan antara performa, biaya, dan kecepatan pemrosesan. Gemini
2.5 Flash juga dijelaskan sebagai hybrid reasoning model yang memiliki pengaturan
thinking budget, sehingga dapat digunakan untuk tugas kompleks dengan tetap
memperhatikan trade-off antara kualitas, biaya, dan latensi [37]. Oleh karena itu, model
ini sesuai untuk kebutuhan yang memerlukan respons cepat, volume permintaan tinggi,
serta pemrosesan dalam jumlah besar.
Dalam konteks Natural Language to SQL (NL2SQL), Gemini 2.5 Flash dapat
digunakan untuk menerjemahkan pertanyaan bahasa alami menjadi query SQL
berdasarkan informasi skema basis data yang diberikan melalui prompt. Dibandingkan

lebih besar. Dengan karakteristik tersebut, Gemini 2.5 Flash dapat digunakan untuk
melihat kemampuan model yang lebih kuat dalam memahami pertanyaan,
memanfaatkan konteks skema, dan menghasilkan SQL yang sesuai.

2.2.4 Prompting
Prompting adalah teknik memberikan instruksi, konteks, dan masukan tertentu
kepada LLM agar model menghasilkan keluaran sesuai dengan tugas yang diinginkan.
Prompt dapat berisi perintah, pertanyaan, contoh, batasan format jawaban, maupun
informasi tambahan yang dibutuhkan model. Melalui prompting, LLM dapat diarahkan
untuk mengerjakan tugas tertentu hanya dengan memberikan instruksi atau konteks pada
masukan, tanpa perlu melakukan pelatihan ulang. Pada LLM, informasi yang diberikan
dalam prompt menjadi konteks utama yang digunakan model ketika menghasilkan
jawaban.
Dalam tugas Natural Language to SQL (NL2SQL), prompt umumnya memuat
instruksi untuk menghasilkan SQL, pertanyaan pengguna, dan informasi skema basis
data. Skema basis data diperlukan karena model harus mengetahui tabel, kolom, tipe
data, dan relasi yang dapat digunakan untuk membentuk query SQL. Beberapa
pendekatan NL2SQL juga menambahkan informasi pendukung, seperti evidence,
contoh pasangan pertanyaan dan SQL, atau aturan khusus terkait format
keluaran [14, 18]. Kualitas prompt dapat memengaruhi kemampuan model dalam
memilih tabel, kolom, kondisi, dan relasi yang sesuai dengan pertanyaan pengguna.
Secara umum, terdapat beberapa bentuk prompting, seperti zero-shot prompting,
few-shot prompting, dan chain-of-thought prompting. Pada zero-shot prompting, model
hanya menerima instruksi dan masukan tanpa contoh penyelesaian. Pada few-shot
prompting, model diberikan beberapa contoh agar dapat mengikuti pola jawaban yang
diharapkan [38]. Sementara itu, chain-of-thought prompting mendorong model untuk
menghasilkan langkah-langkah penalaran sebelum memberikan jawaban akhir [39].
Dalam NL2SQL, pemilihan isi prompt, terutama informasi skema yang disertakan,
menjadi penting karena SQL yang dihasilkan harus sesuai dengan struktur basis data.
2.2.5 Schema Linking dan Schema Pruning
Schema linking adalah proses menghubungkan kata atau maksud dalam
pertanyaan bahasa alami dengan elemen skema basis data yang relevan, seperti tabel dan
kolom [10]. Dalam tugas NL2SQL, pengguna umumnya menggunakan istilah yang
mudah dipahami manusia, sedangkan basis data menggunakan nama tabel dan kolom
yang lebih teknis. Sebagai contoh, pertanyaan ‘nama pelanggan” perlu dikaitkan dengan
kolom seperti customer_name pada tabel customers. Proses schema linking
membantu sistem menentukan bagian skema yang berkaitan dengan pertanyaan
pengguna sebelum membentuk query SQL.
Schema pruning adalah proses mengurangi atau menyederhanakan skema basis
data dengan memilih elemen skema yang dianggap relevan terhadap pertanyaan
22

--- PAGE 36 ---
pengguna. Pada tugas NL2SQL berbasis LLM, skema basis data biasanya dimasukkan
ke dalam prompt agar model mengetahui struktur data yang tersedia. Namun, jika
seluruh skema dimasukkan, terutama pada basis data yang besar, masukan model
menjadi panjang dan memuat banyak informasi yang tidak berkaitan langsung dengan
pertanyaan. Oleh karena itu, schema pruning digunakan untuk membuat konteks skema
lebih ringkas [12].
Schema pruning memiliki hubungan erat dengan schema linking. Schema linking
berperan dalam menemukan tabel dan kolom yang berkaitan dengan pertanyaan,
sedangkan hasil keterkaitan tersebut dapat digunakan dalam schema pruning untuk
menentukan bagian skema yang perlu dipertahankan atau diabaikan. Dalam konteks ini,
schema pruning dapat dipahami sebagai proses penyusunan konteks skema berdasarkan
elemen-elemen yang dianggap paling relevan terhadap pertanyaan.
Meskipun dapat mengurangi ukuran konteks, schema pruning harus dilakukan
secara hati-hati. Jika terlalu banyak bagian skema dihapus, model dapat kehilangan
informasi penting yang dibutuhkan untuk menghasilkan SQL yang benar, seperti tabel
penghubung, primary key, foreign key, atau relasi JOIN. Sebaliknya, jika skema yang
diberikan terlalu lengkap, model perlu memproses banyak informasi yang mungkin
tidak relevan. Tantangan utama dalam schema pruning adalah menjaga keseimbangan
antara keringkasan skema dan kelengkapan informasi yang dibutuhkan model.
2.2.5.1 Schema Pruning Berbasis Tabel
Schema pruning berbasis tabel merupakan pendekatan pemangkasan skema yang
menjadikan tabel sebagai unit utama seleksi. Pada pendekatan ini, sistem memilih tabel-
tabel yang dianggap relevan terhadap pertanyaan pengguna dan menghapus tabel lain
yang tidak berkaitan dari konteks masukan. Pendekatan ini dapat mengurangi ukuran
skema secara signifikan, terutama pada basis data yang memiliki banyak tabel. Dalam
konteks NL2SQL berbasis LLM, pemilihan subset skema atau sub-database yang lebih
kecil dapat membantu model berfokus pada bagian basis data yang lebih relevan terhadap
pertanyaan [40]. Namun, jika tabel yang terpilih memiliki banyak kolom, konteks yang
diberikan kepada model masih dapat memuat informasi yang tidak seluruhnya relevan
terhadap pertanyaan.
2.2.5.2 Schema Pruning Berbasis Kolom
Schema pruning berbasis kolom merupakan strategi pemangkasan skema yang
menjadikan kolom sebagai unit utama dalam proses seleksi skema. Pendekatan ini
menilai relevansi setiap kolom terhadap pertanyaan pengguna. Kolom yang memiliki
keterkaitan dengan pertanyaan dipertahankan, sedangkan kolom yang tidak relevan
dapat dihapus dari konteks masukan. Dengan demikian, skema yang diberikan kepada
23

--- PAGE 37 ---
model menjadi lebih ringkas, tetapi tetap diarahkan untuk mempertahankan informasi
yang dibutuhkan dalam pembentukan SQL.
Pendekatan berbasis kolom penting karena sebagian besar komponen SQL
bergantung langsung pada pemilihan kolom. Kolom dapat berperan sebagai atribut
keluaran pada klausa SELECT, kondisi penyaringan pada klausa WHERE, atribut
pengelompokan pada GROUP BY, atribut pengurutan pada ORDER BY, maupun
sebagai bagian dari kondisi relasi pada JOIN. Hilangnya satu kolom penting dapat
menyebabkan SQL yang dihasilkan menjadi tidak tepat, terutama jika kolom tersebut
digunakan sebagai atribut keluaran, kondisi filter, atau penghubung relasi antartabel.
Namun, schema pruning berbasis kolom juga memiliki tantangan. Tidak semua
kolom penting disebutkan secara eksplisit dalam pertanyaan bahasa alami. Beberapa
kolom, seperti primary key dan foreign key, sering kali tidak muncul dalam pertanyaan
pengguna, tetapi tetap dibutuhkan untuk membentuk relasi antar tabel. Sebagai contoh,
pertanyaan yang meminta informasi pelanggan dan pesanan mungkin hanya
menyebutkan atribut seperti nama pelanggan atau tanggal pesanan, tetapi SQL yang
benar tetap membutuhkan kolom kunci seperti customer_id untuk menghubungkan
tabel customers dan orders. Jika kolom-kolom tersebut terhapus pada proses
pemangkasan, model dapat kesulitan menghasilkan JOIN yang benar.
2.2.6 Mandatory Key Preservation (MKP)
Mandatory Key Preservation (MKP) dapat dipahami sebagai strategi tambahan
dalam schema pruning yang bertujuan mempertahankan kolom kunci dan kolom
penghubung antartabel yang penting dalam pembentukan SQL. Dalam basis data
relasional, kolom seperti primary key dan foreign key berperan dalam menunjukkan
hubungan antartabel. Keberadaan kolom-kolom tersebut dapat diperlukan ketika query
SQL melibatkan operasi JOIN, meskipun tidak selalu disebutkan secara eksplisit dalam
pertanyaan pengguna.
Gagasan untuk mempertahankan informasi relasional dalam proses seleksi
skema sejalan dengan pendekatan berbasis graf pada tugas Text-to-SQL. Safdarian et
al. [11] membangun graf skema berdasarkan relasi foreign key, kemudian menggunakan
algoritma pencarian jalur untuk mengidentifikasi urutan tabel dan kolom yang perlu
dihubungkan dalam pembentukan SQL. Pendekatan tersebut menunjukkan bahwa relasi
antartabel dan jalur JOIN merupakan informasi penting dalam proses schema linking,
terutama pada basis data berskala besar.
Pada pendekatan schema pruning berbasis kolom, pemilihan kolom umumnya
dilakukan berdasarkan tingkat relevansi kolom terhadap pertanyaan pengguna. Kolom
yang memiliki kemiripan langsung dengan pertanyaan cenderung lebih mudah
dipertahankan, sedangkan kolom kunci seperti primary key dan foreign key dapat
24

--- PAGE 38 ---
memperoleh skor relevansi yang rendah karena sering kali hanya berfungsi sebagai
penghubung relasional. Kondisi ini dapat menyebabkan kolom kunci tidak ikut
disertakan dalam konteks skema, padahal kolom tersebut dibutuhkan untuk membentuk
relasi antartabel dalam SQL.
MKP berkaitan dengan upaya menyeimbangkan pengurangan konteks masukan
dan kelengkapan informasi skema. Pengurangan skema yang terlalu agresif dapat
menyebabkan elemen penting tidak ikut disertakan dalam konteks dan berpotensi
menurunkan kualitas SQL yang dihasilkan [12]. Oleh karena itu, strategi ini menjadi
penting karena SQL yang benar tidak hanya bergantung pada kolom yang disebutkan
dalam pertanyaan, tetapi juga pada relasi antartabel yang diperlukan untuk mengakses
data secara tepat.
2.2.7 Information Retrieval
Information retrieval (IR) merupakan proses untuk menemukan informasi yang
relevan dari sekumpulan data atau dokumen tak terstruktur (biasanya berupa teks)
berdasarkan kebutuhan informasi pengguna [41, 42]. Dalam konteks pencarian teks,
sistem IR menerima query sebagai masukan, kemudian menghitung tingkat relevansi
antara query tersebut dengan dokumen atau unit informasi yang tersedia di dalam
koleksi. Hasil pencarian tersebut biasanya dikembalikan dan disusun berdasarkan skor
relevansi, sehingga dokumen atau informasi yang secara komputasi dianggap paling
sesuai dengan query akan ditempatkan pada urutan teratas [42].
Dalam konteks pencarian teks, relevansi antara query dan dokumen dapat
dihitung melalui pendekatan leksikal maupun semantik. Pendekatan leksikal menilai
relevansi berdasarkan kecocokan kata atau istilah secara eksplisit antara query dan
dokumen, sedangkan pendekatan semantik menilai relevansi berdasarkan kedekatan
makna meskipun kata yang digunakan tidak selalu sama.
Dalam tugas NL2SQL, konsep IR dapat digunakan untuk membantu memilih
bagian skema basis data yang berkaitan dengan pertanyaan pengguna. Setiap elemen
skema, seperti tabel atau kolom, dapat direpresentasikan sebagai teks melalui nama
tabel, nama kolom, tipe data, atau deskripsi tambahan. Representasi tersebut kemudian
dibandingkan dengan pertanyaan pengguna untuk menentukan elemen skema yang perlu
dipertahankan dalam konteks masukan model.

2.2.7.3 Hybrid Retrieval
Hybrid retrieval merupakan pendekatan pencarian yang menggabungkan lebih
dari satu metode retrieval. Pendekatan ini dapat digunakan untuk mengombinasikan
pencarian leksikal dan pencarian semantik agar hasil pencarian menjadi lebih
relevan [13]. Pencarian leksikal seperti BM25 termasuk dalam pendekatan sparse
retrieval karena merepresentasikan teks berdasarkan kemunculan term secara eksplisit.
Sementara itu, pencarian semantik berbasis embedding termasuk dalam pendekatan
dense retrieval karena merepresentasikan teks dalam bentuk vektor padat yang
menangkap kedekatan makna antara query dan dokumen.
Kedua pendekatan tersebut dapat saling melengkapi dalam proses pencarian
informasi [46]. BM25 dapat menangkap kecocokan istilah secara langsung, sedangkan
embedding retrieval dapat menangkap kemiripan makna meskipun kata yang digunakan
tidak sama. Kombinasi keduanya dapat digunakan untuk memperoleh skor relevansi
yang mempertimbangkan aspek leksikal dan semantik.

2.2.8 Dataset dan Benchmark pada Text-to-SQL
Dataset dan benchmark memiliki peran penting dalam penelitian text-to-SQL
karena digunakan untuk mengevaluasi kemampuan model dalam menerjemahkan
pertanyaan bahasa alami menjadi query SQL. Berbagai benchmark telah dikembangkan
untuk menguji kemampuan model pada skenario yang berbeda, mulai dari pertanyaan
sederhana pada satu tabel hingga pertanyaan lintas domain yang melibatkan banyak
tabel, relasi skema, dan kebutuhan penalaran tambahan. Beberapa benchmark yang
umum digunakan dalam penelitian text-to-SQL antara lain WikiSQL, Spider, dan BIRD.
2.2.8.1 WikiSQL
WikiSQL merupakan salah satu benchmark awal dalam penelitian text-to-SQL
yang berisi pasangan pertanyaan bahasa alami dan SQL pada tabel berbasis
Wikipedia [26]. Benchmark ini banyak digunakan untuk mengevaluasi kemampuan
model dalam menghasilkan SQL sederhana. Namun, WikiSQL umumnya berfokus pada
query terhadap satu tabel sehingga belum sepenuhnya merepresentasikan kompleksitas
basis data relasional yang melibatkan banyak tabel dan relasi skema.
2.2.8.2 Spider
Spider merupakan benchmark text-to-SQL lintas domain yang dirancang untuk
mengevaluasi kemampuan generalisasi model terhadap basis data yang tidak muncul
30

--- PAGE 44 ---
pada data pelatihan [24]. Berbeda dari WikiSQL, Spider menggunakan skema basis data
yang lebih kompleks dan melibatkan banyak tabel, sehingga model perlu memahami
hubungan antartabel serta menghasilkan SQL yang lebih beragam. Spider menjadi salah
satu benchmark penting dalam penelitian text-to-SQL karena mendorong evaluasi pada
skenario lintas domain dan kompleksitas SQL yang lebih tinggi.
2.2.8.3 BIRD (Big Bench for Large-Scale Database Grounded Text-to-SQLs)
BIRD (Big Bench for Large-Scale Database Grounded Text-to-SQLs) merupakan
benchmark NL2SQL yang dirancang untuk mengevaluasi kemampuan model dalam
menghasilkan SQL pada basis data berskala besar dan lebih mendekati kondisi nyata.
Benchmark ini terdiri atas 12.751 pasangan data text-to-SQL dan 95 basis data dengan
ukuran total 33,4 GB yang mencakup 37 domain profesional [14]. Dataset BIRD dibagi
menjadi tiga bagian, yaitu 9.428 data train, 1.534 data development, dan 1.789 data test.
Berbeda dari benchmark seperti Spider dan WikiSQL yang lebih banyak menekankan
pemahaman terhadap struktur skema dan SQL, BIRD menghadirkan tantangan yang
lebih dekat dengan skenario nyata, seperti penggunaan basis data berukuran besar,
pemahaman terhadap nilai di dalam basis data, pemanfaatan pengetahuan eksternal,
serta efisiensi SQL yang dihasilkan [14].
Setiap data pada BIRD memuat pertanyaan bahasa alami, skema basis data, SQL
acuan, dan pada beberapa kasus disertai evidence. Evidence merupakan informasi
tambahan yang digunakan untuk membantu menjembatani hubungan antara pertanyaan
pengguna dengan nilai atau konteks tertentu di dalam basis data [14]. Dengan adanya
evidence, model dapat memperoleh petunjuk tambahan dalam memahami maksud
pertanyaan, menghubungkan istilah dalam pertanyaan dengan elemen basis data, serta
menentukan kondisi atau nilai yang perlu digunakan dalam SQL. Oleh karena itu, BIRD
tidak hanya menguji kemampuan model dalam memahami struktur tabel dan kolom,
tetapi juga kemampuan dalam memahami konteks data dan menghasilkan query yang
benar ketika dieksekusi pada basis data.
BIRD mengelompokkan pertanyaan ke dalam tiga tingkat kesulitan, yaitu
simple, moderate, dan challenging. Berbeda dari pendekatan pada dataset seperti Spider
yang menentukan tingkat kesulitan terutama berdasarkan kompleksitas SQL, penentuan
tingkat kesulitan pada BIRD dilakukan melalui penilaian manusia berdasarkan aturan

kesulitan tersebut. Dengan demikian, suatu pertanyaan dapat dianggap sulit bukan hanya

2.2.9 Gold SQL dan Gold Columns
Gold SQL adalah SQL acuan yang digunakan sebagai ground-truth dari suatu
pertanyaan bahasa alami pada dataset NL2SQL. Pada benchmark seperti Spider dan
BIRD, setiap pertanyaan sudah dipasangkan dengan SQL acuan yang menunjukkan
bagaimana pertanyaan tersebut seharusnya diterjemahkan ke dalam query SQL pada
basis data tertentu [14, 24]. SQL acuan ini dapat digunakan untuk menilai hasil SQL
yang dibuat oleh model, baik dengan melihat kesesuaian bentuk query-nya maupun
dengan membandingkan hasil eksekusinya.
Selain digunakan untuk evaluasi SQL, Gold SQL juga dapat digunakan untuk
membentuk gold columns. Gold columns adalah kumpulan kolom yang dianggap
diperlukan untuk membuat SQL acuan tersebut. Pada dataset BIRD, informasi gold
columns tidak disediakan secara langsung, sehingga kolom-kolom tersebut perlu
diekstraksi dari Gold SQL. Gold columns digunakan sebagai acuan untuk menilai
apakah metode schema pruning masih mampu mempertahankan kolom-kolom penting
yang dibutuhkan dalam penyusunan SQL.

2.2.10 Metrik Evaluasi
Metrik evaluasi digunakan untuk menilai sejauh mana hasil yang dihasilkan oleh
suatu sistem sesuai dengan acuan yang dianggap benar. Pemilihan metrik perlu
disesuaikan dengan karakteristik tugas yang dikaji, karena setiap metrik dapat
menekankan aspek yang berbeda, seperti ketepatan, kelengkapan, kesesuaian keluaran,
maupun efisiensi penggunaan token.
Dalam pencarian informasi, metrik seperti precision, recall, dan F-score umum
digunakan untuk menilai hubungan antara hasil yang diambil oleh sistem dan item
relevan yang seharusnya ditemukan. Pada tugas NL2SQL, evaluasi juga dapat dilakukan
menggunakan execution accuracy, yaitu kesamaan hasil eksekusi antara SQL prediksi
dan SQL acuan pada basis data yang sama [14, 24]. Selain kualitas hasil, efisiensi
penggunaan token juga perlu dievaluasi untuk menilai apakah schema pruning mampu
membuat deskripsi skema menjadi lebih ringkas dan mengurangi jumlah token yang
diproses oleh model. Hal ini relevan karena biaya pemrosesan LLM umumnya
sebanding dengan panjang teks masukan dan keluaran yang diukur dalam jumlah
token [9].

2.2.10.7 Uji McNemar
Uji McNemar merupakan uji statistik non-parametrik yang digunakan untuk
membandingkan dua metode pada data berpasangan dengan keluaran bersifat
kategorikal biner [48]. Uji ini sesuai digunakan ketika dua metode dievaluasi pada
sampel yang sama dan setiap sampel menghasilkan dua kemungkinan keputusan,
misalnya benar atau salah. Dalam evaluasi model, uji McNemar juga dapat digunakan
untuk membandingkan performa dua model atau metode berdasarkan perbedaan hasil
prediksi pada sampel yang sama [49].
Dalam evaluasi NL2SQL, hasil prediksi SQL dapat dikategorikan sebagai benar
atau salah berdasarkan execution accuracy. Prediksi dianggap benar apabila SQL
prediksi menghasilkan keluaran eksekusi yang sama dengan SQL acuan, sedangkan
prediksi dianggap salah apabila hasil eksekusinya berbeda atau SQL prediksi tidak dapat
dieksekusi. Dengan karakteristik tersebut, hasil evaluasi dua skenario NL2SQL dapat
dipandang sebagai data berpasangan biner.

dibandingkan. Semakin besar nilai χ2, semakin kecil nilai p, sehingga semakin kuat
bukti bahwa kedua skenario menghasilkan perbedaan keputusan.
Keputusan uji dilakukan dengan membandingkan nilai p terhadap taraf
signifikansi yang ditentukan. Apabila nilai p lebih kecil dari taraf signifikansi, maka
perbedaan hasil antara dua skenario dinyatakan signifikan secara statistik. Sebaliknya,
apabila nilai p lebih besar atau sama dengan taraf signifikansi, maka perbedaan hasil
antara dua skenario tidak dinyatakan signifikan secara statistik.
2.2.10.8 Efisiensi Token
Efisiensi token merupakan aspek evaluasi yang berkaitan dengan jumlah token
yang digunakan saat interaksi dengan model. Pada penggunaan LLM, jumlah token
berpengaruh terhadap panjang konteks yang diproses, kebutuhan komputasi, serta biaya
penggunaan model. Semakin besar informasi yang diberikan ke dalam prompt, semakin
besar pula jumlah token masukan yang perlu diproses oleh model, sehingga kebutuhan
sumber daya atau biaya pemrosesan juga dapat meningkat [8, 9].
Secara umum, penggunaan token dapat dibedakan menjadi token masukan dan
token keluaran. Token masukan (prompt tokens) merepresentasikan jumlah token yang
39

--- PAGE 53 ---
terdapat pada teks masukan yang diberikan kepada model. Token keluaran atau output
tokens merepresentasikan jumlah token yang dihasilkan oleh model, misalnya SQL
sebagai keluaran akhir. Pada model tertentu, penggunaan token juga dapat mencakup
token penalaran (thinking tokens) yang digunakan selama proses internal model.
Dalam tugas NL2SQL, sebagian token masukan berasal dari representasi skema
basis data yang disertakan dalam prompt. Pengurangan konteks skema melalui schema
pruning dapat menurunkan jumlah token masukan, tetapi pemangkasan yang terlalu besar
juga dapat menghilangkan informasi skema yang dibutuhkan oleh model. Karena itu,
efisiensi token perlu dianalisis bersama kualitas SQL yang dihasilkan, sehingga evaluasi
tidak hanya melihat seberapa besar pengurangan token, tetapi juga apakah pengurangan
tersebut masih mampu mempertahankan kualitas SQL.

Berdasarkan perbandingan metode pada Tabel 2.4, pendekatan schema pruning
dinilai paling sesuai karena berkaitan langsung dengan pengaturan konteks skema yang
diberikan kepada LLM. Dalam tugas NL2SQL, skema basis data menjadi bagian
penting dari masukan model karena berisi informasi mengenai tabel, kolom, tipe data,
serta relasi yang diperlukan untuk membentuk SQL. Hal ini sejalan dengan temuan
Rajkumar et al. [17] yang menunjukkan bahwa representasi skema di dalam prompt
berpengaruh besar terhadap kualitas SQL yang dihasilkan. Namun, jika seluruh skema
dimasukkan ke dalam prompt, konteks yang diberikan kepada model menjadi lebih
panjang dan dapat memuat banyak informasi yang tidak relevan. Kondisi tersebut dapat
meningkatkan penggunaan token dan membuat model perlu memproses lebih banyak
elemen skema sebelum menentukan bagian yang benar-benar dibutuhkan. Di sisi lain,
jika skema dikurangi secara tidak tepat, informasi penting yang diperlukan untuk
menyusun SQL dapat ikut hilang. Permasalahan ini juga ditunjukkan oleh Maamari et
al. [12], bahwa proses schema linking atau penyaringan skema dapat menurunkan
performa apabila kolom penting ikut terhapus. Oleh karena itu, schema pruning dipilih
karena dapat digunakan untuk mengurangi ukuran konteks skema, sekaligus tetap
diarahkan untuk mempertahankan informasi penting agar SQL yang dihasilkan tetap
sesuai dengan pertanyaan pengguna.
Dibandingkan dengan fine-tuning, pendekatan schema pruning tidak
membutuhkan proses pelatihan ulang model dan relatif lebih hemat sumber daya
komputasi. Penelitian seperti CodeS oleh Li et al. [15] dan SQL-R1 oleh Ma et al. [16]
menunjukkan bahwa pelatihan tambahan dapat meningkatkan kemampuan model dalam
tugas NL2SQL. Namun, pendekatan tersebut membutuhkan data pelatihan, proses
pelatihan model, serta sumber daya komputasi yang lebih besar. Dengan demikian,
fokus penelitian ini tidak diarahkan pada perubahan kemampuan model melalui
pelatihan tambahan, tetapi pada pengaruh pemilihan konteks skema terhadap hasil
NL2SQL. Selain itu, dibandingkan dengan prompting dan in-context learning secara
umum, schema pruning memiliki proses yang lebih terarah karena skema tidak langsung
dimasukkan secara penuh ke dalam prompt, tetapi dipilih terlebih dahulu berdasarkan
relevansinya terhadap pertanyaan pengguna. DAIL-SQL oleh Gao et al. [18]
menunjukkan bahwa strategi penyusunan prompt dan pemilihan contoh dapat
memengaruhi performa, tetapi pendekatan tersebut tetap berkaitan dengan panjang
konteks dan penggunaan token. Melalui schema pruning, hubungan antara pemilihan
skema, ukuran konteks, penggunaan token, dan akurasi SQL yang dihasilkan dapat
dianalisis secara lebih jelas.
Berdasarkan pertimbangan tersebut, penelitian ini menerapkan schema pruning
berbasis kolom dengan Mandatory Key Preservation (MKP). Pemilihan skema
dilakukan pada tingkat kolom karena kolom merupakan bagian skema yang paling dekat

dengan kebutuhan pembentukan SQL. Kolom dapat digunakan untuk menentukan
atribut yang ditampilkan, kondisi penyaringan data, agregasi, pengurutan, maupun
proses penggabungan antartabel. Namun, pemilihan kolom berdasarkan relevansi
terhadap pertanyaan belum tentu cukup untuk menjaga kelengkapan struktur relasi. Pada
beberapa kasus, kolom yang tidak disebutkan secara langsung dalam pertanyaan tetap

tersebut, MKP diterapkan dengan mempertahankan pasangan kolom kunci yang berada
pada jalur relasi antartabel yang relevan. Dengan pendekatan ini, metode yang
digunakan tidak hanya bertujuan mengurangi ukuran konteks skema, tetapi juga
menjaga ketersediaan informasi relasional yang diperlukan agar LLM memiliki konteks

relevan terhadap pertanyaan pengguna. Pendekatan yang digunakan meliputi embedding

dalam prompt LLM untuk menghasilkan SQL. Evaluasi dilakukan terhadap tiga aspek,
yaitu kualitas hasil schema pruning, kinerja SQL yang dihasilkan oleh model, dan
efisiensi penggunaan token. Kualitas schema pruning dianalisis menggunakan metrik
berbasis kesesuaian kolom, seperti precision, recall, F-score, reduction ratio, dan full
recall rate. Kinerja SQL dievaluasi menggunakan execution accuracy, sedangkan
efisiensi dianalisis berdasarkan jumlah token yang digunakan pada setiap skenario.

skema, serta kemampuan metode dalam mempertahankan seluruh gold columns pada

Kinerja SQL prediksi dievaluasi menggunakan execution accuracy. Metrik ini
menilai apakah SQL prediksi menghasilkan keluaran yang sama dengan gold SQL
ketika dieksekusi pada basis data. Sementara itu, efisiensi penggunaan konteks
dianalisis melalui jumlah token yang digunakan pada setiap skenario pengujian. Dengan
demikian, setiap skenario dapat dibandingkan dari sisi kualitas hasil schema pruning,
akurasi SQL, dan efisiensi penggunaan token.

Tahap ekstraksi gold columns dilakukan untuk memperoleh himpunan kolom

merupakan query jawaban benar untuk setiap pasangan pertanyaan dan basis data. Oleh
karena itu, kolom-kolom yang muncul dalam gold SQL diperlakukan sebagai acuan
untuk menilai apakah proses schema pruning berhasil mempertahankan informasi
skema yang dibutuhkan.
Perlu ditegaskan bahwa gold columns tidak digunakan pada tahap retrieval,

gold columns baru digunakan setelah proses pruning atau prediksi selesai sebagai dasar
penilaian.
Ekstraksi gold columns diperlukan karena kualitas schema pruning tidak dapat
dinilai hanya berdasarkan jumlah kolom yang dipertahankan. Skema yang lebih ringkas
belum tentu lebih baik apabila kolom penting ikut terhapus. Sebaliknya, skema yang
sedikit lebih besar dapat lebih layak apabila mampu mempertahankan kolom yang
benar-benar digunakan dalam gold SQL. Dengan demikian, gold columns menjadi label
evaluasi untuk mengukur kesesuaian antara kolom hasil pruning dan kolom yang
dibutuhkan dalam SQL yang benar.

3.3.4.4 Penentuan Top-K Optimal dengan Embedding-Retrieval
Tahap penentuan top-k optimal dilakukan untuk menentukan jumlah kolom yang
dipertahankan dalam proses schema pruning. Nilai top-k menunjukkan banyaknya
kolom dengan skor relevansi tertinggi yang dipilih sebagai konteks skema. Penentuan
nilai ini penting karena jumlah kolom yang dipertahankan dapat memengaruhi
kelengkapan informasi skema dan panjang konteks yang diberikan kepada LLM.
Pada tahap ini, pengujian dilakukan menggunakan pendekatan embedding
retrieval. Pertanyaan bahasa alami yang digabungkan dengan evidence dan representasi
setiap kolom diubah menjadi vektor menggunakan model all-MiniLM-L6-v2.
Selanjutnya, relevansi antara pertanyaan dan kolom dihitung menggunakan cosine
similarity, sebagaimana telah dijelaskan pada Persamaan 2-3 dan Persamaan 2-4. Kolom
dengan nilai kemiripan tertinggi dipilih sebagai hasil pruning berdasarkan kandidat nilai
top-k yang diuji.
Setiap kandidat nilai top-k dievaluasi dengan membandingkan kolom hasil
pruning terhadap gold columns menggunakan metrik schema pruning yang telah
ditetapkan sebelumnya. Evaluasi ini digunakan untuk melihat pengaruh jumlah kolom
yang dipertahankan terhadap kelengkapan kolom relevan dan tingkat pengurangan
ukuran skema.
Nilai top-k optimal dipilih berdasarkan keseimbangan antara kemampuan
mempertahankan kolom penting dan efisiensi konteks. Nilai top-k yang terlalu kecil
dapat menghasilkan konteks yang lebih ringkas, tetapi berisiko menghapus kolom
penting. Sebaliknya, nilai top-k yang terlalu besar dapat meningkatkan kelengkapan
informasi, tetapi mengurangi manfaat schema pruning. Hasil dari tahap ini digunakan
sebagai dasar pada tahap penentuan nilai lexical weight dalam metode hybrid retrieval.

3.3.4.5 Penentuan Lexical Weight Optimal dengan Embedding + BM25
Tahap penentuan lexical weight optimal dilakukan untuk mengatur kontribusi skor
leksikal dalam metode hybrid retrieval. Setelah nilai top-k ditentukan melalui pendekatan
embedding retrieval, tahap ini dilakukan untuk menguji apakah penambahan skor leksikal
dapat meningkatkan kualitas pemilihan kolom dalam proses schema pruning.
Metode hybrid retrieval menggabungkan skor kemiripan semantik dari
embedding retrieval dan skor kecocokan leksikal dari BM25. Dalam penelitian ini,
BM25 digunakan sebagai sinyal tambahan untuk melengkapi embedding retrieval,
bukan sebagai komponen yang mendominasi proses pemeringkatan kolom. Skor
embedding tetap digunakan untuk menangkap kedekatan makna antara pertanyaan dan
representasi kolom, sedangkan BM25 digunakan untuk menangkap kecocokan istilah
secara eksplisit antara pertanyaan, evidence, dan representasi kolom. Dengan demikian,
pemilihan kolom dapat mempertimbangkan aspek semantik dan leksikal secara
bersamaan.
Skor embedding dihitung menggunakan cosine similarity, sedangkan skor BM25
dihitung berdasarkan kecocokan istilah sebagaimana telah dijelaskan pada Persamaan 2-
5. Skor akhir hybrid retrieval dihitung menggunakan kombinasi skor embedding dan skor
BM25 sebagaimana telah dijelaskan pada Persamaan 2-8. Nilai lexical weight digunakan
untuk mengatur kontribusi BM25 dalam skor akhir tersebut. Semakin besar nilai lexical
weight, semakin besar kontribusi skor BM25 dalam pemeringkatan kolom. Sebaliknya,
semakin kecil nilai lexical weight, semakin besar peran skor embedding.
Pada setiap kandidat nilai lexical weight, kolom diurutkan berdasarkan skor
akhir, kemudian dipilih sejumlah kolom teratas sesuai nilai top-k yang telah ditentukan
pada tahap sebelumnya. Hasil pemilihan kolom dievaluasi menggunakan metrik schema
pruning yang telah ditetapkan sebelumnya. Nilai lexical weight optimal dipilih untuk
memperoleh kombinasi skor semantik dan leksikal yang paling sesuai sebelum
diterapkan pada tahap Mandatory Key Preservation (MKP).
3.3.4.6 Penerapan Mandatory Key Preservation (MKP)
Tahap penerapan Mandatory Key Preservation (MKP) dilakukan setelah
konfigurasi hybrid retrieval diperoleh. MKP digunakan sebagai mekanisme tambahan
untuk menjaga agar kolom kunci relasional tetap tersedia setelah proses schema
pruning. Kolom kunci yang dimaksud mencakup primary key, foreign key, dan kolom
penghubung yang diperlukan untuk membentuk relasi antartabel.
MKP diperlukan karena proses retrieval kolom cenderung memilih kolom yang
memiliki kedekatan semantik atau kecocokan leksikal dengan pertanyaan dan evidence.
Kolom seperti nama, kategori, tanggal, jumlah, atau nilai tertentu dapat memperoleh
58

--- PAGE 72 ---
skor relevansi tinggi karena berhubungan langsung dengan informasi yang diminta.
Sebaliknya, kolom kunci seperti id, primary key, atau foreign key sering tidak
disebutkan secara eksplisit dalam pertanyaan, sehingga dapat memperoleh skor rendah.
Padahal, kolom tersebut dapat diperlukan untuk membentuk operasi JOIN pada SQL.
Dalam penelitian ini, MKP diterapkan secara selektif. Kolom kunci yang
ditambahkan hanya kolom yang berada pada jalur relasi antar tabel terpilih, bukan
seluruh primary key dan foreign key pada basis data. Strategi ini digunakan agar hasil
pruning tetap ringkas, tetapi masih mempertahankan informasi relasional yang
dibutuhkan untuk membentuk operasi JOIN.
Secara konsep, MKP memanfaatkan metadata relasi sebagai graf. Tabel
diperlakukan sebagai simpul, sedangkan hubungan primary key dan foreign key
diperlakukan sebagai sisi yang menghubungkan dua tabel. Melalui graf tersebut, sistem
dapat memeriksa apakah tabel-tabel yang terpilih dalam final columns memiliki jalur
relasi. Jika jalur ditemukan, kolom kunci pada jalur tersebut diidentifikasi dan
ditambahkan apabila belum tersedia dalam hasil pruning.
Dalam penelitian ini, pencarian jalur relasi antar tabel dilakukan menggunakan
Breadth-First Search (BFS) pada graf tidak berbobot. BFS digunakan untuk
menemukan jalur dengan jumlah sisi paling sedikit antara tabel-tabel yang muncul
dalam final columns. Jalur tersebut menunjukkan urutan tabel yang perlu dilalui agar
tabel-tabel terpilih dapat dihubungkan melalui relasi primary key dan foreign key.
Kolom kunci yang ditambahkan tidak ditentukan oleh BFS secara langsung,
melainkan diambil dari metadata relasi yang melekat pada setiap edge dalam jalur yang
ditemukan. Setiap edge menyimpan pasangan kolom primary key dan foreign key yang
menghubungkan dua tabel. Dengan demikian, MKP hanya menambahkan kolom kunci
yang berada pada jalur relasi tersebut, bukan seluruh primary key dan foreign key dari
tabel yang dilewati.

3.3.4.8 Inferensi LLM
Setelah proses penyusunan prompt, tahap inferensi LLM dilakukan untuk
menghasilkan SQL prediksi berdasarkan prompt yang telah disusun. Pada tahap ini,
setiap prompt diberikan kepada model LLM sesuai dengan skenario eksperimen. Model
kemudian menghasilkan keluaran berupa query SQL yang dianggap sesuai dengan
pertanyaan bahasa alami, evidence, dan konteks skema yang diberikan.
Inferensi dilakukan pada setiap variasi skema, yaitu full schema, embedding
retrieval, hybrid retrieval, dan hybrid retrieval dengan MKP. Setiap variasi skema diuji
menggunakan pertanyaan dan basis data yang sama agar hasil antar skenario dapat
dibandingkan secara adil. Dengan demikian, perbedaan hasil SQL prediksi dapat
dianalisis berdasarkan perbedaan konteks skema yang diberikan kepada model.
Model yang digunakan pada tahap inferensi adalah Gemini 2.5 Flash dan
LLaMA 3.2 3B Instruct. Gemini 2.5 Flash digunakan melalui layanan API, sedangkan
LLaMA 3.2 3B Instruct dijalankan secara lokal. Pada kedua model, prompt diberikan
dalam format pesan yang sama agar perbedaan hasil tidak disebabkan oleh perbedaan
struktur prompt, tetapi oleh karakteristik model dan variasi konteks skema yang diuji.
Keluaran yang diharapkan dari model adalah SQL akhir dalam bentuk teks biasa.
Sesuai instruksi pada pesan system, model diarahkan untuk tidak memberikan
penjelasan tambahan, format markdown, atau teks lain di luar query SQL. SQL prediksi
yang dihasilkan kemudian disimpan bersama informasi skenario eksperimen, model
yang digunakan, dan metadata sampel. Hasil inferensi ini selanjutnya digunakan pada
tahap ekstraksi dan normalisasi SQL prediksi sebelum dilakukan evaluasi.

4.6 Kelebihan dan Kekurangan Penelitian
Berdasarkan hasil eksperimen yang telah dilakukan, penelitian ini memiliki
beberapa kelebihan dan kekurangan. Kelebihan dan kekurangan yang dibahas berfokus
pada hasil penelitian, karakteristik metode, serta faktor yang memengaruhi performa
model dalam tugas NL2SQL.
4.6.1 Kelebihan Penelitian
Penelitian ini memiliki beberapa kelebihan. Pertama, penelitian ini melakukan
schema pruning tanpa menggunakan LLM pada tahap pemilihan skema. Dibandingkan
pendekatan yang menggunakan LLM untuk melakukan schema pruning atau schema
linking, pendekatan ini lebih efisien karena LLM tidak perlu memproses full schema
terlebih dahulu untuk memilih bagian skema yang relevan. Dalam penelitian ini, LLM
hanya digunakan pada tahap inferensi SQL, sedangkan pemilihan kolom dilakukan
melalui kombinasi embedding retrieval, BM25, dan MKP.
Kedua, penelitian ini mengevaluasi pengaruh penyajian konteks skema dari dua
sisi, yaitu kualitas hasil schema pruning dan performa akhir NL2SQL. Evaluasi schema
pruning digunakan untuk melihat kelengkapan serta efisiensi kolom yang dipertahankan,
sedangkan execution accuracy digunakan untuk menilai kebenaran SQL yang dihasilkan
model. Dengan demikian, hasil penelitian tidak hanya menunjukkan perubahan akurasi
akhir, tetapi juga menjelaskan bagaimana kualitas skema hasil pruning memengaruhi
performa model.
Ketiga, penelitian ini menunjukkan bahwa penerapan MKP dapat menjadi
kompromi antara kelengkapan skema, akurasi, dan efisiensi token. Pada konfigurasi
utama, hybrid retrieval dengan MKP mampu meningkatkan kelengkapan skema hasil
pruning dibandingkan hybrid retrieval tanpa MKP, menjaga execution accuracy agar
tetap mendekati full schema, serta menurunkan penggunaan token dibandingkan
skenario full schema. Hal ini menunjukkan bahwa mempertahankan kolom kunci dan
kolom penghubung dapat membantu menjaga informasi relasional penting tanpa harus
memberikan seluruh skema kepada model.

KESIMPULAN DAN SARAN
5.1 Kesimpulan
Berdasarkan tujuan penelitian dan hasil eksperimen yang telah dilakukan,
penelitian ini menghasilkan beberapa kesimpulan sebagai berikut:
1. Pendekatan schema pruning berbasis kolom dengan embedding retrieval dan
hybrid retrieval embedding-BM25 mampu mengurangi ukuran konteks skema
tanpa menggunakan LLM sebagai komponen utama dalam proses seleksi skema.
Pada konfigurasi utama, kedua pendekatan tersebut menghasilkan reduction ratio
sebesar 47,84%. Dibandingkan embedding retrieval, hybrid retrieval
menghasilkan pemilihan kolom yang lebih baik karena menggabungkan
kedekatan semantik dan kecocokan leksikal. Hal ini terlihat dari peningkatan nilai
recall, F score, dan full recall rate dengan nilai reduction ratio yang tetap sama.
6
2. Penerapan Mandatory Key Preservation (MKP) membantu mempertahankan
struktur relasional pada skema hasil pruning. Penambahan MKP pada hybrid
retrieval meningkatkan recall menjadi 95,61%, F score menjadi 78,02%, dan full
6
recall rate menjadi 84,55%. Meskipun reduction ratio menurun menjadi 44,48%,
penurunan tersebut menunjukkan adanya tambahan kolom kunci dan kolom
penghubung antartabel yang dipertahankan untuk menjaga kelengkapan struktur
relasional.
3. Pengaruh schema pruning terhadap kualitas SQL dan efisiensi token berbeda pada
setiap model LLM. Pada LLaMA 3.2 3B Instruct, hybrid retrieval dengan MKP
menghasilkan execution accuracy tertinggi sebesar 25,55%, sedikit lebih tinggi
dibandingkan full schema sebesar 25,10%. Pada Gemini 2.5 Flash, full schema
menghasilkan akurasi tertinggi sebesar 62,39%, sedangkan hybrid retrieval
dengan MKP memperoleh 61,08%. Namun, hasil uji McNemar menunjukkan
bahwa selisih antara full schema dan MKP tidak signifikan secara statistik, baik
pada LLaMA (p = 0, 645) maupun Gemini (p = 0, 145). Dengan demikian, MKP
belum terbukti lebih unggul secara signifikan dibandingkan full schema, tetapi
mampu menghasilkan performa yang sebanding secara statistik dengan
penggunaan token yang lebih efisien. Pada Gemini 2.5 Flash, hybrid retrieval
dengan MKP menghasilkan rata-rata total token paling rendah sebesar 906,84
token per pertanyaan, lebih rendah dibandingkan full schema sebesar 1.296,60
token. Efisiensi ini berkaitan dengan rata-rata thinking token yang lebih rendah,
sehingga menunjukkan bahwa konteks skema yang ringkas tetapi tetap lengkap
secara relasional dapat membantu proses penalaran model menjadi lebih efisien.

Sebaliknya, hilangnya informasi relasional pada skema hasil pruning dapat
meningkatkan kebutuhan penalaran internal model.
Secara keseluruhan, penelitian ini menunjukkan bahwa schema pruning yang
efektif tidak cukup hanya mengurangi jumlah token dalam prompt. Metode yang
digunakan juga perlu mempertahankan relevansi kolom dan kelengkapan struktur
relasional skema. Dalam penelitian ini, kombinasi embedding retrieval, BM25, dan
MKP menjadi konfigurasi yang paling seimbang dibandingkan skenario lainnya.
5.2 Saran
Berdasarkan hasil penelitian yang telah dilakukan, beberapa saran untuk
penelitian selanjutnya adalah sebagai berikut.
1. Penelitian selanjutnya dapat mengembangkan strategi schema pruning secara
adaptif. Jumlah kolom atau detail informasi skema dapat disesuaikan berdasarkan
kompleksitas pertanyaan, jumlah tabel yang berpotensi digunakan, atau struktur
relasi pada basis data. Dengan cara tersebut, konteks yang diberikan dapat tetap
ringkas untuk pertanyaan sederhana, tetapi tetap cukup lengkap untuk pertanyaan
yang membutuhkan SQL lebih kompleks.
2. Penelitian selanjutnya dapat mengembangkan pendekatan retrieval yang lebih
mempertimbangkan kebutuhan pembentukan SQL, bukan hanya kemiripan antara
pertanyaan dan representasi kolom. Dengan pendekatan tersebut, proses
pemilihan kolom diharapkan mampu menangkap kolom-kolom yang relevan
secara semantik maupun struktural, sehingga kualitas skema hasil pruning dapat
meningkat.
3. Penelitian selanjutnya dapat mengombinasikan penelitian ini dengan strategi
peningkatan kemampuan model atau strategi inferensi, seperti fine-tuning,
few-shot prompting, maupun penambahan sample values. Fine-tuning dapat
digunakan untuk menyesuaikan model dengan pola pertanyaan dan SQL pada
tugas NL2SQL, terutama pada model berukuran kecil. Sementara itu, few-shot
prompting dapat memberikan contoh pasangan pertanyaan dan SQL di dalam
prompt agar model memiliki acuan dalam membentuk kueri. Penambahan sample
values juga dapat membantu model memahami nilai yang mungkin muncul pada
kolom tertentu, sehingga kesalahan dalam menerjemahkan kondisi atau nilai dari
pertanyaan dapat dikurangi.
